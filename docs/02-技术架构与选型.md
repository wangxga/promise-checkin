## 二、技术栈选型与理由

### 2.1 前端：uni-app + Vue3 + TypeScript + Vite + Pinia

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | **uni-app** | 一套代码可同时编译出**微信小程序 + H5 + App**。MVP 虽只发小程序，但未来想推广或做家庭分享 H5 时零成本复用。 |
| 视图层 | **Vue3 `<script setup>`** | 组合式 API，逻辑复用清晰，生态成熟。 |
| 语言 | **TypeScript** | 类型安全，长期项目必备，减少低级 bug。 |
| 构建 | **Vite** | uni-app 官方推荐，开发热更新极快。 |
| 状态管理 | **Pinia** | Vue3 官方推荐，比 Vuex 更轻，TS 支持好。 |
| UI 组件库 | **uni-ui** 或 **uv-ui** | uni-app 官方/社区主流组件库，兼容多端。 |
| 请求封装 | **自封装 uni.request** | 统一处理 baseUrl、token 注入、错误码、loading。 |

> 不选原生小程序开发的原因：原生只能跑微信，未来扩展 H5/App 要全部重写；uni-app 几乎零成本多端，且语法与 Vue 一致，开发效率高。

### 2.2 后端：Node.js + Koa2 + TypeScript

| 项 | 选择 | 理由 |
|---|---|---|
| 运行时 | **Node.js 20 LTS** | 长期支持版，性能稳定。 |
| Web 框架 | **Koa2** | 比 Express 更轻量、洋葱模型中间件清晰、天然 async/await；适合自建小型项目。 |
| 语言 | **TypeScript** | 前后端同语言同类型系统，DTO 类型可前后端共享（通过 `shared/types` 目录）。 |
| ORM | **Prisma** 或 **TypeORM** | 倾向 **Prisma**：类型推断强、迁移工具好用、Schema 即文档；TypeORM 装饰器风格也是备选。 |
| 参数校验 | **zod** 或 **joi** | 倾向 zod：与 TS 结合最好，可从 schema 推导类型。 |
| 日志 | **pino** + **winston**（可选） | pino 性能极好，结构化 JSON 日志便于排查。 |
| 配置 | **dotenv** + 环境变量分层 | dev/prod 配置隔离。 |
| 进程管理 | **PM2** | 守护进程、自动重启、日志切割、零停机重载。 |

### 2.3 数据层：MySQL 8.0 + Redis 7

| 项 | 选择 | 理由 |
|---|---|---|
| 主库 | **MySQL 8.0** | 关系型天然契合"计划-打卡"强结构化数据；事务保证"打卡时扣减次数"的原子性；JSON 字段支持灵活配置（schedule_config）。 |
| 缓存/队列 | **Redis 7** | JWT 黑名单、限流计数、P1 阶段的订阅消息任务队列、统计结果缓存。 |
| 字符集 | **utf8mb4** | 完整支持 emoji（备注、计划名可能含 emoji）。 |
| 时区 | **UTC 存储 + 应用层按 `Asia/Shanghai` 展示** | 避免跨时区问题，小程序用户都在国内统一时区。 |

> 不选 PostgreSQL 的原因：MySQL 在国内云服务器镜像源丰富、运维资料多、个人项目更轻。功能上两者对本项目都够用。

### 2.4 鉴权方案：微信登录 + JWT

```
┌─────────┐  1.wx.login()   ┌─────────┐  2.code          ┌─────────┐
│ 小程序   │ ───────────────▶│ 前端封装 │ ───────────────▶│ 后端    │
│ 客户端   │                 │         │                  │ /auth   │
└─────────┘                 └─────────┘                  └────┬────┘
     ▲                                                       │
     │ 6.存储 token                                          │ 3.code2Session
     │   (uni.setStorage)                                    ▼
     │                                              ┌─────────────────┐
     │                                              │  微信开放平台     │
     │  5.返回 JWT                                  │  api.weixin.qq  │
     │ ◀────────────────────────────────────────────│  .com           │
                                                    └─────────────────┘
                                                          │ 4.返回 openid
                                                          │   + session_key
                                                          ▼
                                              后端：openid 查/建 user
                                                    → 签发 JWT(含 userId)
```

**JWT 设计**：
- Payload：`{ userId, openid, iat, exp }`
- 有效期：access token 7 天，过期后用 refresh token（30天）刷新；
- 登出：把 token 加入 Redis 黑名单到过期时间。
- 密钥：环境变量 `JWT_SECRET`，至少 32 位随机串。

**为什么不用 session + cookie**：小程序场景下 JWT 更合适，无状态、易扩展、跨端通用（H5/App 都能用）。

## 四、关键设计决策记录

### Q1：为什么自建服务器而不用微信云开发？
- **优势**：完全可控，便于后续做 H5 版本（云开发只服务微信端），便于沉淀后端技术能力。
- **代价**：需自行处理 ICP 备案、HTTPS、鉴权、运维（详见 06-部署与运维）。
- **用户已选**：自建服务器（基于现有云服务器 + 域名）。

### Q2：为什么用 MySQL 而不是 MongoDB？
- 计划和打卡记录是**强结构化**数据，关系明确（一对多），事务需求明确（打卡要原子扣减次数）。
- MySQL 的 JSON 字段已足够承担"灵活配置"需求，不需要 MongoDB 的全文档模型。

### Q3：打卡次数为什么用「冗余字段 + 定时校对」而非实时 COUNT？
- `plans.used_count` 冗余存储已打卡数，查询计划列表时**避免 JOIN + COUNT**，性能好。
- 每日凌晨定时任务校对 `used_count = 实际 COUNT(checkins WHERE done)`，防止数据漂移。
- 写入打卡记录时用事务保证「插入 checkins + 更新 used_count」原子性。

### Q4：为什么数据模型预留 family/member 字段但 MVP 不暴露？
- MVP 严格聚焦"个人自用"快速验证；但 `plans.family_id`、`checkins.member_id` 字段先建好（默认 NULL）。
- 这样升级到家庭共享时**无需数据迁移**，只需后端加权限校验 + 前端加 UI。

## 五、性能与安全基线

### 性能
- 计划列表接口 < 200ms（含进度统计）
- 打卡接口 < 100ms
- 日历视图单月数据 < 300ms
- 数据库单表数据量预估：单用户 100 计划 × 100 记录 = 1 万行，全表百万级，索引可轻松覆盖。

### 安全
- 全站 HTTPS（Let's Encrypt 免费证书）
- 接口鉴权：除 `/auth/login` 外全部需要 JWT
- 接口限流：单用户 60 次/分钟（Redis 计数）
- SQL 注入：ORM 参数化查询，禁用拼接
- XSS：备注等用户输入前端转义展示
- 敏感信息：手机号脱敏存储（中间四位打码）
- 错误信息：生产环境不返回堆栈，统一错误码
