# 03 - 数据库设计

> 项目：**如约打卡**（promise-checkin）
> 数据库：MySQL 8.0 · 字符集 utf8mb4 · 排序规则 utf8mb4_unicode_ci
> 时区：UTC 存储，应用层按 Asia/Shanghai 展示

## 一、ER 关系总览

```
┌──────────┐ 1     N ┌──────────┐
│  users   │─────────│  plans   │
│  用户     │         │  计划     │
└──────────┘         └────┬─────┘
      │                     │ 1
      │                     │
      │                     │ N
      │                ┌────▼─────┐
      │                │ checkins │
      │                │ 打卡记录  │
      │                └──────────┘
      │
      │ 1        N ┌────────────┐ N        1 ┌────────────┐
      └────────────│ family_     │────────────│  families  │
                   │ members     │            │  家庭(预留) │
                   └────────────┘            └────────────┘
```

**核心关系**：
- `users` 1 : N `plans`（一个用户多个计划）
- `plans` 1 : N `checkins`（一个计划多条打卡记录）
- `families` / `family_members` —— **MVP 预留**，不暴露 UI

> 数据模型以 `packages/server/prisma/schema.prisma` 为唯一真相源，本文档与之对齐。

## 二、表结构详解

### 2.1 `users` — 用户表

```sql
CREATE TABLE `users` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `openid`        VARCHAR(64)  NOT NULL                COMMENT '微信openid（唯一标识）',
  `unionid`       VARCHAR(64)  DEFAULT NULL            COMMENT '微信unionid（跨产品识别，可选）',
  `nickname`      VARCHAR(64)  DEFAULT NULL            COMMENT '昵称',
  `avatar_url`    VARCHAR(512) DEFAULT NULL            COMMENT '头像URL',
  `phone`         VARCHAR(20)  DEFAULT NULL            COMMENT '手机号（脱敏：138****1234）',
  `phone_raw`     VARCHAR(64)  DEFAULT NULL            COMMENT '手机号加密串（微信加密手机号原文）',
  `family_id`     BIGINT UNSIGNED DEFAULT NULL         COMMENT '所属家庭ID（预留，MVP为NULL）',
  `status`        TINYINT      NOT NULL DEFAULT 1      COMMENT '状态：1正常 0禁用',
  `last_login_at` DATETIME     DEFAULT NULL            COMMENT '最后登录时间',
  `created_at`    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
  `updated_at`    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `users_openid_key` (`openid`),
  KEY `users_family_id_idx` (`family_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

**字段说明**：
- `openid`：微信生态唯一标识，建唯一索引。首次登录时自动创建用户。
- `phone` / `phone_raw`：MVP 暂不采集（登录时不强制授权手机号）。
- `family_id`：**MVP 始终为 NULL**，待 P2 家庭功能上线启用。

### 2.2 `plans` — 打卡计划表（核心）

```sql
CREATE TABLE `plans` (
  `id`                BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `user_id`           BIGINT UNSIGNED NOT NULL                COMMENT '所属用户ID',
  `family_id`         BIGINT UNSIGNED DEFAULT NULL            COMMENT '所属家庭ID（预留）',
  `name`              VARCHAR(64)  NOT NULL                   COMMENT '计划名称',
  `type`              VARCHAR(20)  NOT NULL DEFAULT 'custom'  COMMENT '类型：course/medicine/measure/fitness/learning/custom',
  `color`             VARCHAR(16)  NOT NULL DEFAULT '#007AFF' COMMENT '主题色（hex）',
  `total_count`       INT UNSIGNED DEFAULT NULL               COMMENT '总次数；NULL=无限次（如量血压）',
  `initial_done_count` INT UNSIGNED NOT NULL DEFAULT 0        COMMENT '起始进度（虚拟计数）：装App前已完成次数，只影响进度展示，不补造历史记录',
  `done_count`        INT UNSIGNED NOT NULL DEFAULT 0         COMMENT 'App内实际完成次数（冗余字段，由syncPlanCounts重算）',
  `missed_count`      INT UNSIGNED NOT NULL DEFAULT 0         COMMENT '缺席次数（冗余字段，由syncPlanCounts重算）',
  `absence_consumes`  TINYINT(1)   NOT NULL DEFAULT 0         COMMENT '缺勤是否计入配额消耗：0否1是',
  `time_mode`         VARCHAR(10)  NOT NULL DEFAULT 'fixed'   COMMENT '时间模式：fixed固定/flexible不固定',
  `schedule_config`   JSON         DEFAULT NULL               COMMENT '固定排期配置，详见下方说明',
  `overdue_handling`  VARCHAR(16)  NOT NULL DEFAULT 'keep_pending' COMMENT '逾期处理：keep_pending保留/auto_missed自动标记缺席',
  `overdue_grace_hours` INT UNSIGNED NOT NULL DEFAULT 24      COMMENT '逾期宽限期（小时），仅overdue_handling=auto_missed时生效',
  `record_value`      TINYINT(1)   NOT NULL DEFAULT 0         COMMENT '是否记录数值：0否1是（量血压=1）',
  `value_unit`        VARCHAR(16)  DEFAULT NULL               COMMENT '数值单位：mmHg/ml/个/次',
  `start_date`        DATE         DEFAULT NULL               COMMENT '计划开始日期',
  `end_date`          DATE         DEFAULT NULL               COMMENT '计划结束日期（无限次可空）',
  `status`            VARCHAR(16)  NOT NULL DEFAULT 'active'  COMMENT '状态：active进行中/archived归档/completed完成',
  `remark`            VARCHAR(255) DEFAULT NULL               COMMENT '计划备注',
  `created_at`        DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`        DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  `deleted_at`        DATETIME(3)  DEFAULT NULL               COMMENT '软删除时间（NULL=未删除）',
  PRIMARY KEY (`id`),
  KEY `plans_user_id_status_idx` (`user_id`, `status`),
  KEY `plans_user_id_type_idx` (`user_id`, `type`),
  KEY `plans_family_id_idx` (`family_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='打卡计划表';
```

#### 与旧设计的关键变化
| 旧字段（已废弃） | 新字段 | 说明 |
|---|---|---|
| `used_count`（单一计数器） | `done_count` + `missed_count` | 拆成两个独立冗余字段，由 `syncPlanCounts` 全量重算 |
| `icon`（图标标识） | **删除** | 改用 `type` + `color` 组合呈现，不再单独存 icon |
| — | `initial_done_count` | **新增**：起始进度（虚拟计数），解决"计划已开始才装 App"的痛点 |
| — | `absence_consumes` | **新增**：缺勤是否计入配额消耗（多口径计数开关） |
| — | `overdue_handling` / `overdue_grace_hours` | **新增**：逾期自动处理策略 |

#### `schedule_config`（JSON）结构说明

**场景1：固定课表（按周几）**
```json
{
  "rules": [
    { "weekday": 2, "time": "18:00" },
    { "weekday": 6, "time": "10:00" }
  ]
}
```
> `weekday`：1=周一 … 7=周日（ISO 8601）

**场景2：每日定时（吃药、量血压）**
```json
{
  "rules": [
    { "every": "day", "time": "08:00" },
    { "every": "day", "time": "20:00" }
  ]
}
```

**场景3：不固定时间（flexible）**
```json
null
```
> 用户随时手动打卡，无自动排期。

> 注：旧设计中的"每周 N 次但不固定哪天"（`every: "week"` + `minTimes`）**M1 未实现**，待后续迭代。

#### `type` 枚举说明
| 值 | 含义 | 典型配置 |
|---|---|---|
| `course` | 课程（兴趣班） | total_count=有限，time_mode=fixed |
| `medicine` | 服药 | total_count=有限或NULL，time_mode=fixed |
| `measure` | 测量（血压血糖等） | total_count=NULL，record_value=1 |
| `fitness` | 健身/运动 | total_count=NULL |
| `learning` | 学习（背单词） | total_count=NULL，record_value=1 |
| `custom` | 自定义 | 任意 |

> type 只影响默认配置建议，**不绑定死业务规则**——所有计划行为由各自的配置字段（absenceConsumes/overdueHandling 等）决定。

### 2.3 `checkins` — 打卡记录表

```sql
CREATE TABLE `checkins` (
  `id`                     BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `plan_id`                BIGINT UNSIGNED NOT NULL                COMMENT '所属计划ID',
  `user_id`                BIGINT UNSIGNED NOT NULL                COMMENT '操作用户ID（冗余，便于权限校验）',
  `member_id`              BIGINT UNSIGNED DEFAULT NULL            COMMENT '被打卡成员ID（预留，如大宝/二宝）',
  `scheduled_date`         DATE         NOT NULL                   COMMENT '计划应打卡日期（用户本地时区，不参与UTC换算）',
  `scheduled_time`         VARCHAR(8)   DEFAULT NULL               COMMENT '计划应打卡时间 HH:mm（固定排期时有值）',
  `status`                 VARCHAR(16)  NOT NULL DEFAULT 'pending' COMMENT '状态：done已完成/missed缺席请假/pending待打卡',
  `actual_time`            DATETIME(3)  DEFAULT NULL               COMMENT '实际打卡时间（status=done时填）',
  `value`                  DECIMAL(10,2) DEFAULT NULL              COMMENT '记录数值（如血压120.00）',
  `remark`                 VARCHAR(255) DEFAULT NULL               COMMENT '备注（请假原因/打卡说明）',
  `source`                 VARCHAR(16)  NOT NULL DEFAULT 'scheduled' COMMENT '来源：scheduled按排期/retroactive事后补录',
  `adjustment_type`        VARCHAR(16)  DEFAULT NULL               COMMENT '调整类型：reschedule调整排期/makeup补打/NULL未调整',
  `original_scheduled_date` DATE        DEFAULT NULL               COMMENT '调整排期前的原定日期（首次调整时冻结，追溯用）',
  `original_scheduled_time` VARCHAR(8)  DEFAULT NULL               COMMENT '调整排期前的原定时间',
  `created_at`             DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`             DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  `deleted_at`             DATETIME(3)  DEFAULT NULL               COMMENT '软删除时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `checkins_plan_id_scheduled_date_scheduled_time_key` (`plan_id`, `scheduled_date`, `scheduled_time`)
    COMMENT '同一计划同日同时段唯一；flexible模式scheduled_time=NULL，MySQL多NULL不冲突',
  KEY `checkins_plan_id_scheduled_date_idx` (`plan_id`, `scheduled_date`),
  KEY `checkins_user_id_status_idx` (`user_id`, `status`),
  KEY `checkins_status_scheduled_date_idx` (`status`, `scheduled_date`) COMMENT '逾期扫描任务用'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='打卡记录表';
```

#### 与旧设计的关键变化
| 旧设计 | 新设计 | 说明 |
|---|---|---|
| `scheduled_time` 类型 `TIME` | `VARCHAR(8)` | 改为字符串 "HH:mm"，便于序列化和前端处理 |
| — | `source` | **新增**：区分按排期打卡 vs 事后补录 |
| — | `adjustment_type` | **新增**：标记记录是否经过调整（reschedule/makeup） |
| — | `original_scheduled_date/time` | **新增**：调整排期时冻结原定时间，用于追溯 |

**关键字段说明**：
- `scheduled_date`：**始终是用户本地时区日期**（YYYY-MM-DD），不参与 UTC 换算。这是与"UTC 存储"总原则的例外——日期粒度按本地时区，避免跨日歧义。
- `source`：`scheduled`（系统按排期生成的槽位）/ `retroactive`（用户事后补录）。补录与实时打卡在数据上可区分。
- `adjustment_type`：`reschedule`（调整过排期，original 字段有值）/ `makeup`（从 missed 补打为 done）/ `NULL`（未调整）。

## 四、关键约束与业务规则

### 4.1 计划与打卡的关系
- **固定排期（fixed）**：建计划时**立即生成未来 14 天**的 `pending` 槽位；之后由定时任务（`scheduleGenerator`）每日续期补充。
- **不固定（flexible）**：用户点"+打卡"时实时插入一条 `done` 状态记录，`scheduled_date` = 当天。
- **无限次数计划**（`total_count IS NULL`）：无完成概念，永远 `active`，用户主动归档。
- **有限次数计划**：进度达到 100%（`consumed >= total_count`）时，**M1 不自动转 completed**，需用户手动归档（自动完成逻辑待后续迭代）。

### 4.2 多口径计数派生（核心设计）

进度不再用单一 `used_count`，而是按配置派生多口径（实现见 `shared-utils/mapper.ts` 的 `calcProgress`）：

```
总已完成 totalDone = initial_done_count + done_count
已消耗配额 consumed = totalDone + (absence_consumes ? missed_count : 0)
剩余配额 remain    = total_count - consumed        （无限计划为 null）
进度 progress     = consumed / total_count          （无限计划为 null）
```

- `initial_done_count` 参与 `totalDone` 和 `consumed`，但**不补造历史 checkin 记录**（日历/列表里看不到那 N 次，它们只影响进度数字）。
- `absence_consumes` 决定缺席是否消耗配额：开启则请假也"花掉"一节课，关闭则只按实际完成计。

### 4.3 打卡状态流转

```
              打卡(done)            撤销(pending)
  pending ──────────────▶ done ◀──────────────
     │                                          ↑
     │ 请假(missed)                              │
     ▼                                          │
  missed ──────补打(makeup)─────────────────────┘
```

- 三态 `pending`/`done`/`missed` 之间可任意流转（用户改主意）。
- **调整排期**（`adjustSchedule`）：改单次记录的 date/time，首次调整时冻结 `original_scheduled_*`，标记 `adjustment_type=reschedule`。
- **补录**（`retroactiveDone`）：事后补某天为 done。已有 missed 记录则转为 done 标 `makeup`；无记录则新建 done 标 `source=retroactive`。

### 4.4 计数一致性保证

不再用"同事务 ±1 增量"，改为**事务后全量重算**：

1. 写打卡记录走 `$transaction`（保证 checkin 写入原子性）。
2. 事务提交后调用 `syncPlanCounts(planId)`，**全量重算**：
   - `done_count = COUNT(checkins WHERE status='done' AND plan_id=?)`
   - `missed_count = COUNT(checkins WHERE status='missed' AND plan_id=?)`
3. 兜底：**每日凌晨定时校对任务**（`countReconcile`），**增量校对**（仅过去 24h 有 checkin 变更的计划），双口径重算。

> 设计取舍：全量重算比 ±1 增量稍慢但更稳健，永远不会因并发/异常导致计数漂移；配合定时校对兜底。

### 4.5 逾期自动处理（overdueScanner 任务）

对 `overdue_handling = 'auto_missed'` 的计划：
- 定时任务（每小时）扫描 `status=pending` 的记录。
- 截止时间 = `scheduled_date + scheduled_time + overdue_grace_hours`。
- 超时则 `pending → missed`，remark 自动填"逾期未打卡（自动标记）"，随后 `syncPlanCounts` 重算。

对 `overdue_handling = 'keep_pending'` 的计划：pending 永不自动变化，由用户手动处理。

## 六、数据量预估与扩展性

| 指标 | 单用户预估 | 1万用户预估 |
|---|---|---|
| plans 行数 | ~10 | ~10万 |
| checkins 行数 | ~500（10计划×50次） | ~500万 |

- **500 万行 checkins**：MySQL + 上述索引完全无压力，单查询 < 50ms。
- 若未来破百万用户，可考虑：plans/checkins 按 `user_id` 分片（Sharding），或按年月分区（Partitioning）。MVP 阶段不需要考虑。
